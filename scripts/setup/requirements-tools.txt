# Pinned Python TOOLS layer — installed by scripts/setup/install_python_tools.sh
# into the project venv ($ASTRO_VENV, default /opt/astro-venv). NEVER system pip
# (Kali enforces PEP 668).
#
# SEPARATE FROM requirements.txt ON PURPOSE. requirements.txt is the MEASUREMENT
# layer the repo's own scripts import (astropy/numpy/scipy/PIL) — breaking it
# breaks the chain. This file is the TOOL layer: candidate instruments answering a
# named open question that nothing on the build path imports yet. Keeping them
# apart means a tool experiment cannot take the chain down with it.
#
# EVERY ROW NEEDS A LIVE QUESTION, and every EXCLUSION is a decision with a reason.
# An installed tool nobody drives is debt; a capability sitting unnoticed is the
# opposite failure and this repo has measured it repeatedly (`seqtilt`, SWarp's
# weight map, `grid_ramp.py`). Name the question, and delete the row when it closes.
#
# ===========================================================================
# THERE ARE EXACTLY TWO INSTALL LANES ON THIS RIG, AND NO THIRD — MEASURED.
# `autoconf`, `automake` and `libtool` are ABSENT and installing them needs root
# (`make` and `gcc` ARE present). So autotools-based Debian sources — PSFEx,
# SCAMP — CANNOT be built from `apt-get source` here, however reachable the source
# package is. The two lanes are:
#   (a) PyPI       pin `name==version`; capture artifact sha256 via
#                  `pip install --dry-run --report`.
#   (b) Debian .deb  pin the .deb sha256 against the archive `Packages` index plus
#                  transitive deps, extract, run via `LD_LIBRARY_PATH`.
# Stated here so the next person does not try `dpkg-buildpackage`, hit the same
# wall, and rediscover it.
# ===========================================================================
#
# MEASURED COSTS (`pip install --dry-run`, 2026-08-14). The pinned MEASUREMENT
# layer is NOT moved by any of these — astropy 8.0.1, numpy 2.3.5, scipy 1.17.1
# and Pillow 12.2.0 all resolve "already satisfied".
#
#   sip_tpv            3      galsim             5      astropy_healpix    2
#   piff              13      reproject         20      torchmfbd         37

# ===== INSTALLED =============================================================

# --- Gates a live route, and the route is the largest measured defect we have.
# SWarp CANNOT read SIP: a 3-char compare truncates RA---TAN-SIP to TAN, and its
# distortion gate needs PV terms SIP does not carry, so it applies nothing and
# warns about nothing. MEASURED from source AND confirmed by SWarp itself — an
# identical output canvas and CRVAL to nine decimals from TAN-SIP and from
# SIP-stripped, while TPV moves it 22x8 px. sip_tpv's FORWARD direction is a
# symbolic sympy substitution, not a fit: exact to 1.118e-11 px max over 3600
# points and FLAT in field radius, against a distortion-stripped positive control
# reading 13.82 px and growing to the corner. Only route around the blindness.
sip_tpv==1.1

# --- Pairs with PSFEx and retires a documented transcription trap.
# `galsim.des.DES_PSFEx` reads a PSFEx `.psf` directly and evaluates the PSF at an
# arbitrary position. TOOLS.md records that PSFEx exposes NO position-resolved
# shape, so any comparison must re-derive one — and that its polynomial basis order
# is [1, X, X2, Y, XY, Y2], not the order a reader assumes, which transposes the
# whole field model if taken wrong. GalSim does that re-derivation as a maintained
# library, so the trap cannot arise. Wheel, no C++ build.
galsim==2.8.5

# --- HARD PIN, AND WITHOUT IT sip_tpv DOES NOT IMPORT AT ALL.
# `sip_tpv/__init__.py:3` does `import pkg_resources` at module load, purely to
# populate `__version__`. setuptools REMOVED pkg_resources at 81, and galsim pulls
# setuptools 84 transitively — so installing the two together yields
# `ModuleNotFoundError: No module named 'pkg_resources'` and a package that
# installs cleanly and cannot be imported. MEASURED here: the install reported
# "Successfully installed … sip_tpv-1.1 …" and the import check then went RED,
# which is the whole reason that check exists. setuptools' own deprecation warning
# states the fix verbatim: "pin to Setuptools<81".
setuptools==80.9.0

# --- PINNED EXPLICITLY BECAUSE IT IS DATE-VERSIONED AND ARRIVES TRANSITIVELY.
# `astropy-iers-data` republishes continuously (installed here: 0.2026.7.13.0.54.2;
# PyPI current at time of writing: 0.2026.8.10.0.32.39). It is a transitive
# dependency of astropy and therefore of nearly everything above, which is exactly
# why it gets left unpinned — and an unpinned date-versioned package means the
# environment drifts on every rebuild. Pinning it is what makes "reproducible from
# a clone" true rather than nearly true.
astropy-iers-data==0.2026.7.13.0.54.2
